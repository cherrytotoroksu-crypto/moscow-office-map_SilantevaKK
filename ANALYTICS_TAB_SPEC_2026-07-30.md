# Спецификация: аналитическая вкладка (4 блока)

Дата: 2026-07-30. Статус: спецификация. По задаче — ровно 4 блока (не общая
5-вкладочная аналитика, которую предлагал Codex в
`REMAIN_INTEGRATION_HANDOFF_2026-07-29.md`, раздел «Аналитика для проекта» —
та версия шире и остаётся как справочная идея на будущее, см. «Соотношение
с более широкой аналитикой Codex» в конце).

## Общее правило источника данных

Блоки 1–3 считаются по **общему слою проектов** (`all_projects_layer`) —
им не важно, есть ли у проекта лоты в текущем квартале. Блок 4
(средневзвешенная цена) считается **только по квартальному предложению**
(`data/lots_{quarter}.json`) — у проекта без лотов просто нет цены, это
ожидаемо, не ошибка.

На каждом графике — явная подпись: что за срез, единица измерения, правило
агрегации (сумма/среднее/средневзвешенное), дата данных.

## Блок 1 — KPI по строящимся и проектируемым объектам

Источник: `all_projects_layer`, фильтр `project_status` in
{`Проектируется`, `Строится`}.

| KPI | Расчёт |
|---|---|
| Число проектов | count(distinct `canonical_project_id`) |
| Число корпусов | count(строк с `entity_grain='building'`) |
| Суммарная площадь (будущий ввод) | sum(`gba`), с явной подписью «включает `area_scope=unknown`: N м² — не считать точным» |
| Из них с подтверждённым сроком | count(`input_date_kind='confirmed'`) |
| Из них только заявленный срок | count(`input_date_kind='planned'`) |
| Из них без подтверждённых координат | count(`geometry_quality in ('unverified','unknown')`) |
| Из них только по внешнему источнику | count(`external_only=true`) |
| По девелоперам (топ-5) | count(distinct `canonical_project_id`) group by `developer`, sort desc |

Каждое число с площадью — отдельно показывать долю с `area_scope='unknown'`
(правило «неизвестное не считать нулём» — эта доля не должна тихо
теряться/обнуляться).

## Блок 2 — Площадь по субрынкам / деловым районам

Источник: `all_projects_layer`, группировка по `submarket` и отдельно по
`zone`/`bizFormed`/`bizForming`.

- Столбчатая диаграмма: площадь (сумма `gba`, с учётом `area_scope` —
  считать только записи `area_scope in ('project','building')`, площади
  `area_scope='phase'`/`unknown` показывать отдельным столбцом «неучтено/
  неопределённый охват», не суммировать вместе с остальными).
- Фильтр по `project_status`/`offer_status` (можно смотреть только
  строящееся, только введённое и т.д.).
- ⚠️ Явная подпись (по аналогии с предупреждением Codex про Remain): «один
  объект может относиться к нескольким деловым районам — суммы по районам
  не обязательно аддитивны, если это так для конкретных данных».

## Блок 3 — Площадь по годам ввода со статусами

Источник: `all_projects_layer`, группировка по `input_year`, стек по
`project_status` (или по `offer_status` — оба разреза полезны,
переключатель).

- Столбчатая диаграмма с накоплением (stacked bar): ось X — `input_year`,
  высота столбца — сумма `gba`/`office_area`, цвет сегмента —
  `project_status`.
- Отдельная полоса/маркер для записей с `input_quarter=null` («год известен,
  квартал — нет») — не растворять в квартальном разрезе молча.
- Годы с `input_date_kind='planned'` визуально отличать от `confirmed`
  (например, штриховка) — не давать одинаковую уверенность обоим.

## Блок 4 — Средневзвешенная цена по классам и годам

Источник: `data/lots_{quarter}.json` (текущий выбранный квартал, как и
остальная ценовая аналитика проекта сейчас).

- Матрица/линейная диаграмма: строки — `cls` (Prime/A/B+/B), столбцы —
  `input_year` (год ввода здания, к которому относится лот) ИЛИ квартал
  среза — нужно явно выбрать один разрез, оба сразу не показывать на одном
  графике (легко перепутать «цена по году ввода» с «цена по кварталу
  среза»).
- Средневзвешенная цена = sum(`price`×`area`)/sum(`area`) — как и в текущей
  логике проекта (см. существующие расчёты в `index.html`, не меняются).
- Фильтр по каналу (продажа отдельно от аренды — как и везде в проекте).

## Соотношение с более широкой аналитикой Codex

`REMAIN_INTEGRATION_HANDOFF_2026-07-29.md` описывает 5 вкладок («Вся база»,
«Текущее предложение», «Будущее предложение», «Сделки», «Качество данных»)
с более широким набором KPI. 4 блока этой задачи — это по сути ядро вкладок
«Будущее предложение» (блоки 1–3) и «Текущее предложение» (блок 4) из той
более широкой схемы. Вкладки «Сделки» и «Качество данных» в эту задачу не
входили — фиксирую как следующий шаг, не реализую сейчас.

## Нерешённые вопросы

1. Технология графиков — проект уже использует Chart.js (`index.html`, для
   существующей «Динамика по кварталам») — логично продолжать на нём же,
   но явного решения не принималось для этой задачи.
2. Блок 3 (площадь по годам) требует `all_projects_layer` с реально
   заполненными `input_year` по всем ~279 проектам — сейчас только 5
   тестовых записей (см. открытый вопрос №2 в `ALL_PROJECTS_LAYER_SPEC`).
