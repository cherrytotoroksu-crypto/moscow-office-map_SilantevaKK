# Спецификация: общий слой карты «Все офисные проекты Москвы»

Дата: 2026-07-30. Статус: спецификация + тестовая схема. Основано на
`ALL_PROJECTS_MAP_LAYER_SPEC_2026-07-29.md` (Codex), адаптировано под точный
список полей из задачи. См. также `UNIFIED_DATA_ARCHITECTURE_2026-07-30.md`
для общей картины.

## Назначение

Отдельный, самостоятельный слой — не расширение и не замена квартального
предложения. Показывает **всю известную вселенную** офисных проектов Москвы:
проектируемые, строящиеся, введённые, замороженные, отменённые, продавшиеся
целиком, проекты без опубликованных лотов и объекты, известные только из
внешних источников (Remain/Remapp).

Связь с квартальным слоем — только через `canonical_project_id`/
`canonical_building_id`. Слои не имеют права взаимно удалять записи: проект
может быть в общем реестре и отсутствовать в квартальном предложении — это
нормальное состояние, а не ошибка.

## Схема записи

Полная JSON Schema — `data/schema/all_projects_layer.schema.json`, тестовый
набор из 5 записей — `data/test_fixtures/all_projects_layer.sample.json`,
валидатор — `scripts/validate_all_projects_layer.py`
(`tests/test_validate_all_projects_layer.py` — 8 тестов, все проходят).

### ⚠️ Важное уточнение по названиям полей задачи

В задаче поле `project_status` перечислено со значениями «В продаже» /
«Продажи завершены» / «Ещё не вышел в продажу» — по сути это **статус
предложения** (Codex называет его «Статус предложения»), а не стадия
стройки. Отдельно в задаче есть `construction_status` — вот это уже
жизненный цикл объекта (проектируется/строится/введён/...).

Я реализовал именно так, как это выглядит по смыслу задачи:
- **`project_status`** = статус предложения: `В продаже` | `Продажи завершены` | `Ещё не вышел в продажу` | `Не применяется` (последнее значение добавил сверх трёх из задачи — нужно для BTS/аренды/объектов вне канала продажи, без него им некуда деться).
- **`construction_status`** = стадия стройки: `Проектируется` | `Строится` | `Введён` | `Заморожен` | `Отменён` | `Не установлен` (значения взял из `ONLINE_TABLES_AND_STATUS_SPEC_2026-07-29.md`, т.к. в задаче для этого поля значения не перечислены).

Если имелось в виду наоборот (project_status = стадия, а не статус
предложения) — переименовать проще, чем менять логику; сообщите, поправлю.

### Полный список полей (сверх того, что явно перечислено в задаче)

Задача явно перечисляет: `project_status`, `construction_status`,
`input_year`, `input_quarter`, `source`, `source_date`, `verification_status`,
`confidence`, `raw_name`, `canonical_name`, `public_visibility`. Без
дополнительных полей ниже слой не сможет работать как отдельная сущность:

| Поле | Зачем | Из чьей спецификации |
|---|---|---|
| `canonical_project_id` | Устойчивый ключ для связи с квартальным слоем и внешними наблюдениями — без него нельзя ни на что сослаться | Codex |
| `canonical_building_id` | Разделение проекта на корпуса (Бадаевский, STONE-кластеры) | Codex |
| `entity_grain` | `project` или `building` — на каком уровне запись | Codex |
| `aliases` | Известные альтернативные названия (для entity_matches) | Codex |
| `developer`, `address`, `latitude`, `longitude` | Базовые описательные поля — без них слой бесполезен | очевидно из контекста задачи |
| `geometry_quality` | Отдельная (не общая) оценка надёжности координаты | Codex, правило «нельзя одной общей оценкой» |
| `input_date_kind` | `planned`/`confirmed`/`unknown` — заявленный или подтверждённый срок, не путать (явное требование REMAIN_INTEGRATION_HANDOFF) | Codex |
| `cls`, `gba`, `gla`, `office_area`, `area_scope` | Класс/площади + уровень охвата площади (правило: нельзя суммировать площади разных area_scope, см. кейс А101 Прокшино) | Codex + существующая схема classifier.html |
| `zone`, `submarket`, `bizFormed`, `bizForming` | Геотаксономия, совпадает с уже существующей в classifier.html | существующий проект |
| `market_channel` | Массив каналов (sale/rent/coworking/bts/off_market) — не смешивать в одном агрегате | Codex |
| `offer_not_started_reason` | Обязательна при `project_status='Ещё не вышел в продажу'` | Codex, `ONLINE_TABLES_AND_STATUS_SPEC` |
| `external_only` | true — запись существует только благодаря внешнему наблюдению | Codex |
| `quarter_offer_refs` / `quarter_offer_exists` | Ссылки на кварталы с реальными лотами — вычисляемые, не хранить руками | Codex, критично для раздела 3 |
| `qa_status`, `qa_notes` | Итог автоматической проверки | новое, для scripts/validate_all_projects_layer.py |
| `first_seen_at`, `last_verified_at`, `source_count` | История проверки записи | Codex |

## Дубли корпусов/башен — явное правило (по задаче)

**Не объединять автоматически.** Правило, реализованное в схеме и валидаторе:

- Один `canonical_project_id` может встречаться у нескольких записей, если
  они различаются по `canonical_building_id` — это НЕ дубль (пример:
  `badaevsky-west` и `badaevsky-east`, оба `canonical_project_id: "badaevsky"`).
- Повтор одинаковой пары `canonical_project_id` + `canonical_building_id` —
  это дубль, `scripts/validate_all_projects_layer.py` его отклоняет
  (`test_duplicate_canonical_building_id_is_rejected`).
- Объединение по названию/координате без явного правила запрещено (тот же
  принцип, что уже применялся в классификаторе: «Сити-4» и «SEZAR TOWER» —
  разные проекты несмотря на общего девелопера и соседний район).

## Бадаевский — реализация конкретного требования задачи

> «Бадаевский учитывай как один объект в квартальных сводах, но исходные
> корпуса сохрани в общем слое»

Реализовано именно так в `data/test_fixtures/all_projects_layer.sample.json`:
- `badaevsky-west` и `badaevsky-east` — две записи, `entity_grain: "building"`,
  общий `canonical_project_id: "badaevsky"`, разные `canonical_building_id`,
  разные `gba`/`input_year`/`input_quarter` (как и в реальных данных
  classifier.html: 7713/6244 м² Q4 2026 vs 11145/9022 м² Q4 2027).
- Квартальный слой (`data/buildings_*.json`) **не меняется** этой задачей —
  там ленты как были двумя строками, так и остаются технически (это
  production-данные, трогать не просили). Правило «один объект в квартальных
  сводах» относится к будущей агрегации КПИ/аналитики поверх
  `canonical_project_id`, а не к переписыванию существующих файлов.

## Правило отображения (без изменений от Codex)

- подтверждённый проект — обычный маркер;
- внешнее наблюдение без сопоставления (`external_only=true`,
  `verification_status` не `accepted`) — контурный маркер;
- конфликт координат/срока (`qa_status=conflict`) — маркер с предупреждением;
- замороженный (`construction_status=Заморожен`) — штриховка;
- введённый и ушедший с рынка (`construction_status=Введён`,
  `project_status=Продажи завершены`) — отдельный статус, **не удалять**;
- проект без лотов (`quarter_offer_exists=false`) — показывать с подписью
  «предложение не зафиксировано».

## Фильтры общего слоя

`project_status`, `construction_status`, год/квартал ввода (`input_year`/
`input_quarter`), `cls`, `bizFormed`/`bizForming`, `zone`/`submarket`,
`developer`, `source`, `confidence`, наличие предложения в выбранном
квартале (`quarter_offer_exists`), `market_channel`.

## Раздел 3 задачи — квартальные карты vs общий слой

| | Квартальная карта (как сейчас) | Общий слой «Все проекты» |
|---|---|---|
| Что показывает | только проекты с `quarter_offer_exists=true` для выбранного квартала | все проекты независимо от `quarter_offer_exists` |
| Фильтр статуса предложения (`project_status`) | **убрать из UI** — квартальная карта уже подразумевает «в предложении» по построению | доступен как обычный фильтр |
| Фильтры | статус продажи/аренды объекта, класс, цена, площадь (как сейчас) | статус продаж, стадия строительства, год ввода, класс, девелопер, деловой район, субрынок, источник (по задаче) |

Технически: квартальная карта продолжает читать `data/buildings_*.json`/
`lots_*.json` как сейчас (не меняется); общий слой — новый отдельный fetch
нового файла (см. открытые вопросы — формат файла не выбран окончательно).

## Запреты (без изменений от Codex)

- не считать количество проектов по числу строк лотов;
- не удалять проект при исчезновении лотов;
- не суммировать площади корпуса и проекта одновременно;
- не превращать заявленный срок (`input_date_kind=planned`) в подтверждённый;
- не считать отсутствие лотов доказательством отсутствия проекта;
- не смешивать продажу, аренду, сервисные офисы и коворкинги в одном
  `market_channel`-агрегате.

## Публичная/внутренняя граница

`public_visibility` решает по каждой записи; но независимо от него **никогда
не публикуются**: сырые Remain-наблюдения с `verification_status=unverified`,
`qa_notes`, содержимое `qa_flags`. Валидатор уже отклоняет
`public_visibility=public` + `verification_status=unverified`
(`test_unverified_public_record_is_rejected`) — это защита от случайной
публикации неподтверждённых данных, а не полноценная модерация.

## Нерешённые вопросы

1. **Формат хранения общего реестра в проекте** — отдельный
   `data/all_projects_layer.json` (как остальные `data/*.json`) или как
   отдельные объекты в `classifier.html` (как сейчас RAW_DATA/COLORMAP/NOTES)?
   Оба варианта совместимы со схемой, выбор влияет на то, как редактор
   картосхем и онлайн-таблицы будут это читать. Не решаю сам — см. итоговый
   раздел рекомендаций.
2. **Наполнение реестра реальными ~279 проектами** — эта задача даёт только
   схему + 5 тестовых записей. Перенос всех текущих проектов из
   classifier.html в этот формат — отдельный, некороткий заход (нужно
   присвоить `canonical_project_id` каждому, решить `entity_grain` для
   мультикорпусных объектов вроде STONE-кластеров, ASPACE и т.д.).
3. **`quarter_offer_refs`/`quarter_offer_exists` — кто их вычисляет** —
   нужен скрипт, сверяющий `data/buildings_*.json` по кварталам с
   `canonical_project_id`; не реализован (только схема/поле).
