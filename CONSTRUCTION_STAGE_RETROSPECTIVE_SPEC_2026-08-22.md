# Ретроспектива стадий строительства — spec, 2026-08-22

Зафиксировано по прямой просьбе пользователя: «для классификатора мы
добавим ретроспективу по стадиям строительства, чтобы можно было
открыть старый квартал и увидеть стадию строительства с источниками».
Это архитектурное решение — записано явно, чтобы и Claude Code, и Codex
были в курсе до того, как кто-то из них начнёт менять `data/building_dates.json`
или `data/all_projects_layer.json` способом, несовместимым с этим планом.
**Реализация не начата** — это только спецификация.

## Проблема

Сейчас `data/building_dates.json` хранит только 3 точечные даты на
проект (`construction_start_q`, `start_q`, `commission_q`) — самое
свежее известное состояние. Открыть старый квартал (например, Q1 2024)
и увидеть, на какой стадии стройки проект был **именно тогда**, по
**тогдашним источникам**, — нельзя: данные не историзированы, а более
поздние подтверждения (найденные в 2026 году) молча подменяют собой
любое более раннее знание.

Пример риска: `commission_q` для STONE Ходынка 4 подтверждён в 2026-08-22
как 2032 год. Если квартал ввода когда-то поменяется в источнике (перенос
срока), при перезаписи поля старое значение и стоявший за ним источник
пропадут — а ретроспективный просмотр Q1 2024 должен показывать то, что
было известно и подтверждено **на Q1 2024**, а не текущее 2032.

## Цель

Для каждого проекта и каждого квартала — явная, сохранённая с источником
запись: «на этот квартал стадия стройки была такая-то, подтверждено
такого-то числа по такой-то ссылке». Открыв старый квартал в
кодификаторе/классификаторе, пользователь видит стадию **на тот момент**,
а не текущую.

## Сущности

`stage_observation` — новая сущность, отдельная от текущего
`building_dates.json`:

```
{
  "canonical_project_id": "proj-200",       // ссылка на all_projects_layer.json
  "quarter": "202603",                       // квартал, К КОТОРОМУ относится наблюдение
  "stage": "Строится",                       // один из project_status enum (Проектируется/Строится/Введён/...)
  "source": "stone.ru/commercial/hodinka3, разрешение на строительство получено (kommersant.ru/doc/8228995)",
  "source_date": "2026-08-22",               // когда источник ПРОВЕРЕН (не обязательно совпадает с quarter)
  "confidence": "high",                      // high/medium/low — как и в остальном реестре
  "review_notes": null                       // опционально: расхождения/сомнения
}
```

Одному проекту соответствует **N** записей `stage_observation` (по одной
на квартал, где стадия подтверждена) — не одна перезаписываемая строка,
как сейчас в `building_dates.json`.

## Отношение к существующим полям

- `data/building_dates.json` (`construction_start_q`/`start_q`/`commission_q`)
  — **не заменяется**, остаётся источником для деривации
  `input_year`/`input_quarter` через `scripts/build_all_projects_layer.py:
  commission_to_input`. `stage_observation` — дополнительный, более
  гранулярный слой поверх него, не замена.
- `data/all_projects_layer.json`: `project_status` — это ТЕКУЩАЯ стадия
  (последний снимок). `stage_observation` хранит ИСТОРИЮ стадий по
  кварталам — разные назначения, оба поля остаются.
- Квартальные файлы (`buildings_*.json`, `lots_*.json` и т.д.) стадию
  стройки сейчас не хранят вообще (только наличие предложения) — это и
  есть тот пробел, который `stage_observation` закрывает.

## Где хранить (предложение, не решено окончательно)

Вариант А (рекомендуется): `data/stage_observations.json` — плоский
список записей вида выше, один файл, не бьётся по кварталам (как
`building_dates.json` — общий файл на все периоды). Простое чтение,
простая валидация одним скриптом по аналогии с
`scripts/validate_all_projects_layer.py`.

Вариант Б: по кварталу, `data/stage_202603.json` и т.д. — согласуется с
остальными квартальными файлами, но дробит provenance по времени
источника (полей quarter и source_date уже достаточно в варианте А,
дробление по файлам просто добавляет операционных сложностей).

**Решение по варианту — не принято**, нужно обсудить перед началом
реализации (см. «Запреты» ниже).

## UI-ask (кодификатор)

При открытии старого квартала (не только текущего) — карточка проекта
(по аналогии с уже существующей `openSourceCard()` в `codifier.html`)
должна показывать: стадию стройки НА ЭТОТ квартал (если есть
`stage_observation` с `quarter` = выбранный квартал или ближайший
предыдущий с известной стадией), источник, дату проверки. Если для
квартала данных нет — явно показывать «стадия на этот период не
зафиксирована», не подставлять текущую стадию молча.

## Правила (по аналогии с unified_codifier_blueprint / QA_COORDINATION)

- Не сливать `stage_observation` разных кварталов в одну запись —
  каждый квартал со своим подтверждением остаётся отдельной строкой,
  даже если стадия не менялась (можно оптимизировать чтение отдельно,
  но не терять точки наблюдения).
- Не подставлять текущий `project_status` задним числом в старые
  кварталы без отдельного источника на тот период.
- Не удалять и не перезаписывать существующие записи `building_dates.json`
  при построении `stage_observation` — только читать как один из
  источников для деривации, где применимо.
- `data/building_dates.json` продолжает подчиняться отдельному правилу
  (см. `CODEX_AUDIT_REQUEST_2026-08-22.md`, раздел «Правила») — этот
  spec НЕ отменяет это правило, только описывает будущую отдельную
  структуру.

## Статус

`OPEN` — спецификация зафиксирована, реализация (скрипт сборки, UI в
`codifier.html`, первичное наполнение по историческим кварталам) не
начата. Следующий шаг — решить вариант хранения (А/Б выше) и объём
первого прохода по историческим кварталам (сколько кварталов назад
реалистично найти источники).
