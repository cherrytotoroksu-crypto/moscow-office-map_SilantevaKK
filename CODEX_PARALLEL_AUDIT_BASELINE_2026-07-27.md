## Проблемы модели доверия

### 1. Цвет привязан к названию

`COLORMAP` использует `row.name`, а не стабильный идентификатор строки. В таблице 278 строк, но только 256 уникальных названий; найдено 15 групп повторяющихся названий. Одна отметка может окрасить несколько строк с разными ID и даже разными координатами.

Примеры:

- `Multispace Галерея Актер` — две строки с разными координатами;
- `СODE Delegat (1-й Щемиловский 16с2)` — две строки с разными адресами и координатами;
- `Ключ Сретенка` — координата одна, но один адрес относится к Сретенке, другой — к Нижнему Сусальному переулку;
- `Manufaqtury Поклонка` — три строки и две разные точки; общая жёлтая отметка `lat/lng` применяется ко всем;
- `Space Балчуг` — одна строка содержит адрес `повтор`.

### 2. Счётчики и объект COLORMAP небезопасны

Встроенный счётчик считает записи массивов `COLORMAP`, а не фактически отрисованные ячейки. Квартальное поле окрашивает две колонки, но считается один раз; одинаковые названия, наоборот, могут размножать одну метку на несколько строк.

В `COLORMAP.yellow` ключ `Upside Кунцево` объявлен дважды. JavaScript без предупреждения сохраняет только последнее объявление, поэтому более ранняя метка `status` фактически теряется. Для предотвращения подобных ошибок цветовая карта должна храниться в JSON без повторяющихся ключей и проходить структурную проверку.

### 3. Цвет почти не содержит доказательств

Источники в основном остались в памяти прошлых сессий и не связаны с конкретной ячейкой. Поэтому даже зелёный цвет сейчас трудно воспроизвести и проверить независимо.

### 4. Смешаны разные виды уверенности

В одной цветовой системе смешаны:

- внешнее подтверждение истинности;
- исправление значения;
- спорность;
- отсутствие данных;
- вычисление по геослоям;
- совпадение с исходным JSON.

Машинная согласованность не доказывает истинность. Например, район может идеально соответствовать координате, но сама координата может относиться к другому объекту.

### Координатные кластеры

В классификаторе остаются девять исторических строк на известной точке-заглушке `55.755819, 37.617644`. Среди них разные московские адреса, а также записи с названиями «Новосибирск» и «Астана». В актуальном квартале этой заглушки нет, но историческая часть классификатора остаётся недостоверной.

### Согласованность с квартальными JSON

Для каждой строки выполнено сопоставление по `old_id + lastQ`.

- 272 строки имеют единственное совпадение по ID;
- одна строка имеет неоднозначное совпадение;
- пять строк не находятся в заявленном квартальном файле по `old_id`;
- после исключения ожидаемой нормализации названия оператора остаётся 13 строк с содержательным расхождением или проблемой ID.

Высокоуверенные структурные примеры:

- `KW Симонов`: адрес есть в live JSON, но пуст в классификаторе;
- исторические строки «Белой площади» исправлены только в классификаторе, а соответствующие квартальные JSON всё ещё содержат заглушку;
- `Lakes`, `STONE Towers. Tower D`, `STONE Курская`, `Level Нижегородская` расходятся с последним квартальным JSON по статусу или классу — возможно, это обоснованные ручные уточнения, но у них должен быть явный источник;
- пять строк требуют восстановления связи с исходным ID.

Совпадение с JSON означает только отсутствие рассинхронизации, а не внешнее подтверждение истинности.

### Неполное числовое представление

Классификатор не хранит ряд важных live-полей:

- для зданий отсутствуют `volume`, `price`, `lots`;
- для коворкингов отсутствует `vacancy`;
- лоты продажи и аренды не представлены отдельными строками.

Поэтому таблица сейчас не может доказуемо контролировать 20 921 лот продажи, 1 322 лота аренды и соответствие live-агрегатов. Для этих полей нужен отдельный parity-отчёт либо расширение контрольной схемы; визуальное покрытие классификатора для них фактически отсутствует.

## Новая модель проверки

Для каждой комбинации `стабильный row_key + поле` хранить:

- текущее значение или его хеш;
- статус уверенности;
- метод проверки;
- список источников;
- дату доступа;
- проверяющего;
- комментарий о границах применимости источника.

Рекомендуемые статусы:

| Статус | Значение |
|---|---|
| `EXTERNAL_CONFIRMED` | Два независимых источника либо первичный источник плюс независимая проверка |
| `PRIMARY_CONFIRMED` | Один сильный первичный источник |
| `MACHINE_CONSISTENT` | Вычислено или согласовано автоматически, но истинность исходной точки не доказана |
| `SINGLE_SOURCE` | Один вторичный источник |
| `CONFLICT` | Источники расходятся |
| `MISSING` | Значение отсутствует |
| `UNCHECKED` | Проверка не проводилась |

Цвет должен генерироваться из этого реестра. Ключом должен быть стабильный ID строки, а не название.

## Параллельный план Codex

### Поток A — полная машинная проверка

1. Закрыть QA-012.
2. Исправить пять разорванных связей `old_id`.
3. Проверить повторяющиеся названия и отделить повторное наблюдение одной площадки от разных сущностей.
4. Добавить блокирующие тесты геополей, ID, заглушек и parity с источниками.
5. Добавить проверки повторяющихся ключей `COLORMAP` и конфликтов категорий.

### Поток B — актуальные здания

Работать пакетами по 8–10 зданий. Для каждого здания проверять одним заходом:

- сущность, адрес и координаты;
- девелопера и класс;
- GBA/GLA с явным определением охвата площади;
- статус и три даты;
- связь с лотами и кварталами.

Приоритет: сначала 97 актуальных зданий, затем 26 исторических.

### Поток C — актуальные коворкинги

Сейчас это самый слабый сегмент: среди 77 актуальных строк нет ни одного зелёного поля.

Работать пакетами по 10–15 площадок:

- оператор и точное название площадки;
- адрес, БЦ и координаты как единая сущность;
- места и ставка — только с датой наблюдения и источником;
- отдельный `location_id` для площадки и `offer_id` для предложения.

Исторические 78 строк проверять после актуальных.

### Поток D — доказуемость

1. Создать `verification_registry.json`.
2. Импортировать существующие цвета как `legacy_*`, не выдавая их за доказанные.
3. Связывать каждый новый статус с URL или машинным тестом.
4. Отображать в таблице отдельно внешнюю уверенность и машинную согласованность.

## Критерий готовности

Классификатор считается надёжным не тогда, когда большинство ячеек окрашено, а когда:

- 100% актуальных строк имеют стабильный идентификатор;
- 100% геополей машинно согласованы;
- у каждой зелёной ячейки сохранены воспроизводимые источники;
- ключевые поля актуальных объектов имеют внешнее подтверждение;
- любые расхождения между классификатором и каноническими JSON объяснены в реестре;
- автоматические тесты не позволяют вернуть известные заглушки и рассинхронизацию.
- live-поля `price/volume/lots/vacancy` контролируются отдельным воспроизводимым отчётом.
