# Coverage audit: preliminary findings

После разбора структуры файлов установлено:

- `lots_*.json` и `rent_lots_*.json` — словари `project_name -> lots[]`;
- `coworking_*.json` — плоские строки площадок сети, поэтому их `name` нельзя напрямую сравнивать с именем проекта общей карты;
- проверка коворкингов по одному `name` даёт массовые ложные пропуски и требует связки по `network + address + coordinates`.

У продаж после удаления повторов по периодам осталось 14 уникальных кандидатных названий, которых нет по точному нормализованному имени в общей карте. Среди них есть повреждённые кодировкой варианты, а также короткие `A`, `B`, `B+`, которые нельзя автоматически считать проектами без проверки структуры исходного свода.

Вывод: коворкинги нужно сопоставлять площадка-к-корпусу, а продажи — по имени с таблицей aliases и, где возможно, по адресу/девелоперу. Автоматическое добавление 14 кандидатов запрещено до ручной классификации.
