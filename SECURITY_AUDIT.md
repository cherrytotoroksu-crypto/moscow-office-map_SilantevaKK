# Аудит безопасности перед публичным доступом

Дата: 2026-07-30. Цель: коллеги открывают карту по прямой ссылке без
авторизации; служебные данные, исходные таблицы, внутренние QA-файлы и

Репозиторий на момент аудита: `github.com/cherrytotoroksu-crypto/moscow-office-map_SilantevaKK`,
**публичный** (`private: false`, проверено через GitHub API), деплой —
GitHub Actions → GitHub Pages.

### 2. Клиентский код

- **Секреты/ключи/токены**: полный grep по всем HTML/JS/JSON/MD/YML —
  **не найдено**. Клиентский код не хранит и не запрашивает API-ключи;
  сторонние сервисы (Leaflet, тайлы карт, шрифты) не требуют ключей на
  используемых бесплатных эндпоинтах.
- **XSS / `innerHTML`**: в `index.html` ~28 мест вставляют данные из
  `data/*.json` через `innerHTML` (карточка здания, модалки лотов/аренды/
  коворкингов, сравнение зданий). Все данные — из внутренне курируемых
  JSON-файлов, не от пользователей сайта, поэтому классического
  reflected/stored XSS через ввод постороннего человека здесь нет. Тем не
  менее добавлена defense-in-depth: функция `escapeHtml()` и применена к
  карточке здания (`buildingCardRows`) и модалке коворкингов (самые
  «свободнотекстовые» поля: адрес, девелопер, статус, название/сеть/адрес
  коворкинга). **Не покрыто полностью** — модалки лотов продажи/аренды и
  сравнение зданий используют тот же паттерн без экранирования; учитывая
  масштаб (12 900+ строк, десятки мест) и отсутствие реального пользовательского
  ввода как источника XSS, это отложено как P2, не критично для релиза.
- **`URLSearchParams`/query-параметры**: `applyStateFromURL()` читает
  `location.search`, но каждое значение проверяется по allow-list
  (`QUARTERS.some(...)`, `mode === 'sale'|'rent'|'coworking'`,
  `LAYER_CFG[layer]`) до использования — небезопасной прямой вставки
  query-параметров в DOM не найдено.
- **Debug-панели / directory traversal**: отдельного бэкенда нет (чистая
  статика), debug-эндпоинтов нет. Проверено вручную: `../classifier.html` и
  подобные пути на локально поднятом `_site/` возвращают 404 (питоновский
  `http.server` нормализует путь; на GitHub Pages поведение аналогичное для
  статики).
- **Обработка ошибок**: `fetch(...).catch(() => fallback)` уже используется
  в нескольких местах загрузки данных — при сбое подставляется пустое
  значение, а не raw-текст ошибки/стектрейс в DOM.

### 4. Хостинг и HTTP

- **HTTPS**: GitHub Pages отдаёт сайт по HTTPS по умолчанию — без действий с
  нашей стороны, уже выполнено.
- **CSP** добавлена через `<meta http-equiv="Content-Security-Policy">` в
  `index.html` (см. сам файл и комментарий рядом) — разрешает скрипты/стили
  только с `'self'`, `unpkg.com`, `cdn.jsdelivr.net`, `fonts.googleapis.com`;
  шрифты — `fonts.gstatic.com`; тайлы карт — `basemaps.cartocdn.com`,
  `tile.openstreetmap.org`, `server.arcgisonline.com`; `object-src 'none'`;
  `base-uri 'self'`; `form-action 'self'`.
- **`Referrer-Policy`** — задан через `<meta name="referrer" content="strict-origin-when-cross-origin">`.
- **⚠️ Ограничение хостинга (не устранено, требует решения)**: GitHub Pages
  **не позволяет задавать произвольные HTTP-заголовки**. Из-за этого
  недостижимы на текущем хостинге:
  - `X-Content-Type-Options: nosniff` — нет meta-эквивалента;
  - `Permissions-Policy` — нет meta-эквивалента;
  - `frame-ancestors` / защита от clickjacking — `frame-ancestors` в
    `<meta>`-CSP браузеры **игнорируют** (работает только как HTTP-заголовок,
    это ограничение спецификации CSP, не наша недоработка); `X-Frame-Options`
    тоже только заголовок.
  - Полноценный `script-src` без `'unsafe-inline'` — тоже недостижим без
    хостинг-независимого рефакторинга (см. ниже), но это не ограничение
    хостинга, а архитектуры кода.

  Если нужна полная защита по этим пунктам — единственный путь: перенести
  раздачу статики на хостинг с поддержкой кастомных заголовков (Netlify,
  Vercel, Cloudflare Pages — там это делается файлом `_headers`/`vercel.json`
  без смены кода приложения). Это отдельное решение по инфраструктуре, не
  делаю его самостоятельно — см. «Что осталось нерешённым».
- **CORS**: сайт не имеет собственного API/бэкенда — все запросы это `fetch`
  статических JSON-файлов с того же origin. Постороннего происхождения
  (cross-origin) запросов к чужим API в коде нет, поэтому отдельная
  CORS-политика не требуется/не применима.
- **Source maps / debug-режим**: не используются (нет сборки/бандлера,
  чистый HTML+инлайн-JS) — раскрывать через sourcemap нечего.
- **Кеширование**: управляется GitHub Pages автоматически (не настраивается
  нами на этом хостинге).
- **`robots.txt`**: добавлен (`Allow: /`) — теперь под корнем сайта нет
  ничего, что стоило бы прятать от индексации отдельно.

## Что осталось нерешённым (нужно ваше решение)

1. **Репозиторий публичный, история — тоже.** Смена конфигурации деплоя
   (пункт 1) убирает внутренние файлы из *раздаваемого сайта*, но **не** из
   самого GitHub-репозитория — любой человек с URL репозитория (не сайта)
   может открыть `github.com/.../classifier.html`, всю историю коммитов и
   все старые QA-файлы напрямую на GitHub. Секретов/ключей там не найдено, но
   есть внутренняя методология и переписка-в-виде-коммитов. Варианты:
   - сделать репозиторий приватным и раздавать сайт через отдельный хостинг
     (Netlify/Vercel/Cloudflare Pages), который умеет деплоить публичную
     статику из приватного репозитория без авторизации для зрителей —
     закрывает и этот пункт, и ограничение с HTTP-заголовками выше;
   - либо разделить на два репозитория (приватный — вся работа с историей,
     публичный — только `_site`, пушится туда CI);
   - либо принять остаточный риск как есть (секретов нет, только
     методология/аналитика).
   Не выполняю ни один из вариантов сам — смена видимости репозитория и/или
   хостинга затрагивает существующие ссылки коллег и требует вашего решения.
2. **История git не очищена.** Даже если сейчас файл убрать из
   отслеживания, старые коммиты с его содержимым остаются в истории, пока
   её не переписать (`git filter-repo`/BFG) и не сделать force-push. Это
   деструктивная, необратимая для текущих клонов операция — не делаю без
   отдельного явного подтверждения.
3. **Имя и должность реального человека в UI и в имени репозитория.**
   Карта показывает «Ксения Силантьева / Младший аналитик...» прямо в
   интерфейсе, и имя фигурирует в URL репозитория
   (`..._SilantevaKK`). Это не техническая уязвimость, но раз речь о
   публичном доступе — стоит сознательно решить, оставлять ли ФИО и
   должность конкретного сотрудника в публично доступном виде. Не менял
   без согласования (бизнес-логику/UI-тексты трогать не просили).
4. **XSS-экранирование неполное** (см. раздел 2) — модалки лотов
   продажи/аренды и сравнение зданий не обёрнуты в `escapeHtml()`. Низкий
   приоритет (нет пути для постороннего ввода), но можно доделать отдельным
   заходом.
5. **CDN-скрипты без Subresource Integrity (SRI).** Leaflet/markercluster/
   leaflet-draw/xlsx/chart.js грузятся с unpkg.com/jsdelivr.net без
   `integrity="sha384-..."` — если сам CDN или пакет будет скомпрометирован,
   код выполнится без проверки хэша. Не добавил сейчас (риск подобрать
   неверный хэш и сломать загрузку без возможности сразу протестировать все
   версии пакетов) — рекомендую отдельным, тщательно протестированным
   заходом.
6. **Заголовки `X-Content-Type-Options`/`Permissions-Policy`/`frame-ancestors`**
   недостижимы на GitHub Pages (см. пункт 4 выше) — требуют смены хостинга.

## Расчёты, геометрия, бизнес-логика

Не менялись. Единственная логическая правка кода — вырезание
`source`/`last_checked` из **копии** `building_dates.json` при сборке (сам
